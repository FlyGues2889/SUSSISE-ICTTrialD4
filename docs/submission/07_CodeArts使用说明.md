# CodeArts 使用说明

**项目名称**：久坐肩颈腰背科学运动干预助手
**团队**：SUS SISE
**使用形态**：CodeArts 智能体 + 4 个自定义 Skills + 全流程 AI 辅助编码

---

## 一、为什么用 Skills，而不是把逻辑写进接口

产品里最难被复用、也最需要被反复验证的部分是专业判断：24 道题怎么加权、什么分数算高风险、什么条件下必须拦下推荐。这部分逻辑如果写进接口，会带来三个问题：

1. **无法单独验证。** 想验证"总分 24 分是否被拦下"，必须先把服务跑起来、注册账号、逐题提交。
2. **无法离线批量执行。** 36 个方案的 SQL 生成、演示账号的 5 轮历史数据，都需要在没有 HTTP 请求的情况下调用同一套逻辑。
3. **两套实现的风险。** 前端 Mock 模式需要一份可运行的评估逻辑，如果重新写一遍，会出现前端算出 18 分、后端算出 21 分的情况。

因此我们把专业能力封装为 4 个纯函数 Skill，放在项目根目录的 `skills/` 下：

| Skill | 入口函数 | 职责 |
|---|---|---|
| `posture_assessment` | `assess_posture(area, answers)` | 六维度加权评分、问题点提取 |
| `safety_check` | `check_safety(risk_level, red_line_hit, ...)` | 四档分级、就医建议、红线判定 |
| `plan_matcher` | `match_plans(all_plans, risk_level, area, duration, scene)` | 硬过滤 + 加权打分 + Top-3 |
| `qa_responder` | `respond_qa(question, kb_items)` | 字符二元组召回 + 阈值拒答（未命中时由 `app/services/ai.py` 调华为云 AI 兜底） |

另有一个离线脚本 `generate_plans`，用同一套动作模板生成 36 个方案的 SQL，不参与在线请求。

**核心约束：后端路由只做鉴权、参数校验、持久化，不复制任何专业判断。** 这条约束让"改一次权重，前后端同时生效"成为可能。

## 二、Skills 的设计思路

**单一职责。** 评分回答"有多严重"，安全回答"能不能练"。两者拆开，是因为它们的判定阈值不同：分数的四档边界是 12.81 / 18.3 / 23.79，而拦截条件是"红线题 ≥ 2 项**或**总分 ≥ 23.79"。合在一个函数里，边界条件会互相缠绕。

**纯函数、无副作用。** 四个 Skill 都不读数据库、不发网络请求、不依赖全局状态。输入是字典和列表，输出是字典。这让它们可以被 pytest 直接覆盖，也可以被 CLI 脚本直接调用。

**可解释优先。** `plan_matcher` 的权重表（部位 0.4 / 时长 0.3 / 场景 0.2 / 基础 0.1）是硬编码的常量，不是学习出来的参数。理由是推荐理由必须能对用户讲清楚。

**安全优先于转化。** `check_safety` 的返回值里包含"是否允许进入方案推荐"的结论，业务层必须尊重它。这条设计让安全不是一句提示文案，而是一道有拦截权的关卡。

**AI 兜底不越权。** 问答在 Skill 未命中且配置了 `AI_PROVIDER=huawei` 时调用华为云 AI，系统提示词把"不做诊断、出现危险信号直接建议就医、回答 120 字以内"写成硬规则；AI 超时或不可用则回退到固定拒答文案。Skill 本身仍是纯函数，网络调用留在服务层，不影响离线验证。

## 三、AI 辅助开发的落地方式

本项目在 CodeArts 智能体中完成从需求到部署的全流程，主要用法有四种：

1. **Skills 先行。** 先让智能体按"输入/输出/边界条件"写出四个 Skill 与单元测试，再让后端接口调用它们。专业逻辑在还没有 UI 的时候就已经可验证。
2. **双模式同源。** 前端 Mock 模式直接把 Python Skill 的逻辑镜像为 `mock/skills.js`，两边的题库、权重、阈值完全一致，演示环境不需要后端也能跑通完整闭环。
3. **脚本化验证。** 用 `compileall` + 真实 HTTP 端到端脚本验证接口，覆盖注册、评估、方案、收藏、自定义、打卡、问答全链路，而不是只看页面能不能打开。
4. **交付物共写。** 申报书、方案库文档、部署手册等材料与代码放在同一仓库，文档里出现的数字（36 方案、36 动作、9 条指南、单侧满分 36.6）都能被代码或数据库核对。

## 四、规模与效率

| 指标 | 数值 | 说明 |
|---|---|---|
| Skills 代码 | 377 行 / 5 个文件 | 4 个在线 Skill + 1 个离线生成器 |
| 后端代码 | 1102 行 Python | 6 个路由模块 + 缓存/AI 服务 + 数据层 |
| 前端代码 | 3349 行 Vue + 1525 行 JS | 9 个页面 + 自研 UI 组件 + 双模式 API 层 |
| 接口数量 | 18 个 | 认证 3、评估 2、方案 7、训练 3、提醒 2、问答 1 |
| 数据规模 | 36 方案 / 36 动作 / 243 条目 / 9 条指南 | 全部可查询核对 |

**关于提效数据的说明：** 团队没有做严格的对照实验，以下为内部估算口径，不作为精确结论。按传统方式，完成同等范围的工作（双模式前端、四个专业 Skill、18 个接口、演示数据脚本、部署材料、七项申报交付物），一人约需 6–8 周；实际在 CodeArts 智能体中用约 3 周完成，主要节省在四类工作：一是把 PRD 里的规则翻译成代码的机械环节；二是前后端字段对齐与 Mock 数据生成；三是接口端到端验证脚本的编写；四是申报材料的初稿与数字核对。**未节省的部分是专业判断本身**——评估维度、权重、红线标准、方案动作顺序，仍然由团队中运动康复背景的成员确定，智能体负责实现与验证。

## 五、可复现的最小验证路径

```bash
# 1. Skills 逻辑可独立运行
python -c "import sys; sys.path.insert(0,'skills'); from posture_assessment import assess_posture; print(assess_posture('neck', {}))"

# 2. 后端可编译
python -m compileall -q project/backend/app skills

# 3. 前端可构建（上云用 build:cloud，本地演示用 build）
cd project/frontend && pnpm build

# 4. 演示数据可重建
python project/backend/scripts/seed_demo.py --reset
```

这四步不依赖任何外部服务，是评委或后续维护者验证项目可用性的最短路径。
